# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## 1. Overview

This repo contains an open-source, local-first Swift client for AICoven. The goal is:

- No dependency on a custom backend (no login, covens, or user accounts for end users).
- All persistent state (chats, documents, settings) is stored locally on-device.
- The app talks directly to LLM/embedding providers using user-supplied API keys.

The main app code lives under `swift/AICoven/AICoven`. There are also empty top-level `core/`, `features/`, and `infrastructure/` folders that are not currently wired into the build; focus on the `swift/` tree.

## 2. Common commands

### 2.1 Open the project in Xcode

```bash
open swift/AICoven/AICoven\ Local.xcodeproj
```

Most day-to-day development and running is done via Xcode (Cmd+R, Test navigator, etc.).

### 2.2 Build the app from the command line

The primary Xcode project is `swift/AICoven/AICoven Local.xcodeproj` with scheme `AICoven` and configurations `Debug`, `Release`, and `Staging`.

```bash
# Debug build for macOS
xcodebuild \
  -project "swift/AICoven/AICoven Local.xcodeproj" \
  -scheme AICoven \
  -configuration Debug \
  -destination 'platform=macOS' \
  build
```

If you need to target a specific destination, add a `-destination` flag (e.g. an iOS simulator or Mac).

### 2.3 Run tests (XCTest)

The `AICovenTests` directory under `swift/AICoven` contains 18 test files with 41+ test methods covering LLM clients, services, infrastructure, integration scenarios, tooling, and UI smoke tests.

Example CLI test run:

```bash
xcodebuild \
  -project "swift/AICoven/AICoven Local.xcodeproj" \
  -scheme AICoven \
  -configuration Debug \
  -destination 'platform=macOS' \
  test
```

### 2.4 Run a single test (example)

```bash
xcodebuild \
  -project "swift/AICoven/AICoven Local.xcodeproj" \
  -scheme AICoven \
  -configuration Debug \
  -destination 'platform=macOS' \
  -only-testing:AICovenTests/MessageAdapterTests/testSanitizeContent_removesSquareBracketToolCallMarkup \
  test
```

### 2.5 Linting / formatting

A `.swiftlint.yml` configuration exists at the repo root. CI runs SwiftLint and SwiftFormat via `scripts/lint.sh`. Locally:

```bash
# Install tools (if not present)
brew install swiftlint swiftformat

# Run the lint script (format, lint, build, tests)
./scripts/lint.sh
```

## 3. High-level architecture

The Swift client is structured into a few main layers inside `swift/AICoven/AICoven`:

- `App/` – Application entry point and top-level composition.
- `Core/` – Domain models and local-only abstractions (LLM, storage, documents, tools, agents).
- `Features/` – User-facing features grouped by area (Chat, Settings, Documents).
- `Infrastructure/` – Cross-cutting concerns like design system, persistence, and keychain.
- `Services/` – Service layer including ChatService, StoreService, MemoryService, and some legacy services being refactored out.
- `Networking/` – Environment configuration (no backend URLs in the local-first client).
- `Views/`, `ViewModels/`, `Utils/`, `Extensions/` – Older layout still present for some screens and helpers; some of these are being moved into `Features/` and `Core/`.

### 3.1 App entry and navigation

**Key files:**

- `swift/AICoven/AICoven/App/AICovenApp.swift`
  - `@main` entry point for the multiplatform app (iOS + macOS).
  - Creates the root `WindowGroup` and shows `ContentView`.
  - Configures some global appearance (e.g., navigation bar title style).

- `swift/AICoven/AICoven/App/ContentView.swift`
  - Root SwiftUI view for the local-first client.
  - Shows the sign-in, onboarding and unlock screens as needed, then the main view, `HomeView()`.
  - Expects an `AppState` environment object for global state.

- `swift/AICoven/AICoven/Views/Main/HomeView.swift`
  - The main view on every platform: the shell (`ShellRootView`). On the iPad and iPhone it chooses the shell's layout: the split one where `PlatformCapabilities.usesSplitLayout` says (an iPad unless its width is compact), and the phone's otherwise, which always sees compact width; one view either way, so a device that changes between them keeps where it is. Its state is one account's on every platform, and it sets the environment's `isPadLayout`.
  - On the Mac it is the main window: it shows the shell (`ShellRootView`, one split view as the cloud app's; see 3.6), opens the Settings window when asked (`AppState.settingsRequests`), and sends each deep link to its place in Settings.

Agents making navigation changes should do so via these entry views rather than wiring new roots elsewhere.

### 3.2 Core layer (local-first abstractions)

**Location:** `swift/AICoven/AICoven/Core`

This is the local-first backbone intended to replace many backend-oriented services:

- `Core/LLM/`
  - Defines `LLMClient`, a provider-agnostic protocol for chat completions and embeddings.
  - `ToolEnvironment` inspects configured providers and derives per-provider capabilities.
  - Provider implementations for OpenAI, Anthropic, Gemini, OpenRouter (through the OpenAI client at OpenRouter's address), Ollama, and MLX (on-device via Apple Silicon).
  - **`OpenClawLLMClient`** – OpenAI-compatible self-hosted proxy client. Exposes `isLocalEndpoint` (checks `baseURL` against loopback/RFC1918 ranges) and adjusts timeouts (300s/600s for local, 60s/120s for cloud). `baseURL` is `internal` so `ChatService` can inspect it for `isLocalDeployment()` decisions.
  - **`HermesAgentClient`** – the Hermes agent's own API (`/v1/runs`): start a run, follow its events, answer what it asks to be allowed, stop it, read where it stands. Hermes is an agent, not a model: `ChatService.streamMessage` hands a turn whose provider is `hermes` to `Services/HermesTurn.swift`, which follows the run and reports it as the reply loop reports its own turns, so the status line, work trace, approvals and Stop are the same.
  - **`OpenClawGatewayConnection`** (`Core/LLM/Providers/OpenClawGateway.swift`) – one connection to an OpenClaw native Gateway over a web socket, protocol 4: the Gateway's challenge is answered with this device's identity (`OpenClawDeviceIdentity`, an Ed25519 key in the Keychain) and a signature over it; then requests get their answers by id and events arrive in the Gateway's order. An OpenClaw connection has a Gateway address only if the person gives one; without it the connection speaks the OpenAI chat API through `OpenClawLLMClient`. With one, OpenClaw is an agent like Hermes: `ChatService.streamMessage` hands a turn whose provider is `openclaw` to `Services/OpenClawTurn.swift`, which starts the run in the thread's session (`chat.send`), follows its `chat` events, asks the person about each `session.approval` through `ToolApprovals` (this once, or no) and stops the run (`chat.abort`) when the turn is stopped. A run the app was closed on is kept with its turn (`AgentRun`, with the Gateway it was started through) and picked up when its thread is opened: `OpenClawTurn.resume` reads where it stands (`agent.wait`, `chat.history`) and follows it from there.
  - `ModelTemperature` says which models are asked with a temperature: some refuse a request that carries one (OpenAI's reasoning models, Anthropic's from 4.7 on, of any family). A model whose name says it takes none (`takesNoneByName`) is asked without one; any other that refuses it (a 400 naming the temperature) is asked once more without, and, if it then answers, without one for the rest of the app's run. The OpenAI, Anthropic and OpenClaw clients send their chat requests through `ModelTemperature.send`.
  - `GeminiLLMClient` asks for a model as the API names it, `models/<id>` (`resourceName(of:)`), whether the stored id has the prefix (picked from the list) or not (typed, or named in code); what does not read as a model's id is not sent. Its requests, the model listing's (`ProviderAccountService.geminiModelsRequest`) and the image and voice services' carry the key in `x-goog-api-key`, never in the address.
  - `MLXLLMClient` runs models locally via Apple's MLX framework. Handles iOS memory pressure (model eviction after inference, GPU cache limits, `autoreleasepool` for generation). System messages are folded into the first user message for compatibility with strict chat templates (Gemma 2, Phi, etc.).
  - `MLXModelManager` manages a curated model catalog with category (`general`, `coding`, `mobile`), tier (`core`, `specialized`), recommended-for tags, and device-aware filtering (iPhones only see models ≤ 3 GB RAM or `.mobile` category).
  - `MCPToolCallingBenchmark` evaluates a local model's MCP tool-calling accuracy across 10 test cases (web, file, GitHub, shell, Google Drive). Results are persisted in `UserDefaults` and displayed in the MLX settings UI.
  - `MCPToolEmbeddingCache` caches embedding vectors for MCP tool descriptions, enabling semantic tool selection via cosine similarity when many tools are available.
  - `LLMConfiguration.makeEnvironment()` now registers the active MLX model as a `ModelDescriptor` so it participates in routing.

- `Core/Context/`
  - `ContextBuilder` assembles the layered context sandwich for each chat turn.
  - Composes system contract, runtime facts, policies, retrieved memories, thread history, and current message.
  - What a turn's model is told first is who answers (`ContextBuilder.Agent`, given by `ChatService.answeringAgent(roleId:)`): the instructions the person wrote for the coven's agent the turn is for, or for Strix where it is for none, as the cloud app composes its system prompt (the instructions, or "You are <name>, a helpful AI assistant." for none, then its Identity section unless the instructions have one). An agent that cannot be read is answered for by nobody: the turn is told nothing of who answers. An agent run of the app's own gives no agent.
  - A turn handed to an agent of the person's own (Hermes, an OpenClaw Gateway) is not built a context: the agent runs it itself, with its own tools. It is told first what bears on it here, as the cloud app gives such a run its system messages (`ContextBuilder.preface`): who answers, what every agent where the thread is knows (`## Coven Context`), and the memories that bear on the question, matched on this device by their words (the question is not sent to a provider to be embedded: it goes to the agent and nowhere else); nothing of this app's tools, policies or checklist. A Hermes run gets it as the first of its history, as the system's (`ChatService.hermesHistory(from:toldFirst:)`); an OpenClaw run, which takes one text, as its first part under `system:` (`OpenClawTurn.message(_:after:toldFirst:)`), where it gives way before the message does when the whole is too long.
  - Supports device-aware `Limits`: `.mobile` (6 recent messages, 4 memories) for iPhones running local models where RAM is shared with MLX model weights.

- `Core/Routing/`
  - `HeuristicModelRouter` selects the best model per task based on capabilities, user preferences, and context requirements.
  - `findExact(providerID:modelID:)` prioritizes user-selected models from Strix settings before falling back to heuristic routing.
  - `ModelDescriptor` types define model capabilities (context length, tools support, quality tier).
  - Task types include `.chat`, `.summarize`, `.embed`, `.judge`, `.agentStep`, and `.mcpToolCalling` (prefers tool-capable models, falls back to cheapest).

- `Core/Agents/`
  - `AgentRunner` executes bounded multi-step autonomous runs.
  - `AgentProfile` describes agent types, allowed tools, memory scopes, and safety constraints.

- `Core/Tools/`
  - `ToolExecutionService` routes tool calls including shell commands, connected-app tools (GitHub, Google Drive), and MCP server tools. A tool that changes something (a shell command, a file write, a GitHub or Google write, or a tool of an MCP server that the server does not mark as read-only) first asks the person through `ToolApprovals`, which shows one approval at a time beside the thread (`Views/Chat/ApprovalBlock.swift`). An approval asked while the person is composing (the composer has focus and its text changed in the last three seconds, or the on-screen keyboard is up) is held back, and comes in when they send, pause, or leave the composer.

  - The GitHub tools (`github.listRepos`, `getRepo`, `readFile`, `listFiles`, `searchCode`, `getPullRequest`, `listPullRequestFiles`, and the writing `writeFile`, `createBranch`, `createPR`) are named as the cloud app names them (`github.listRepos` is this app's own) and name a repository as it does: one argument, `repo: "owner/name"` (`GitHubToolArguments.repository(in:)`, which also takes `owner` and `repo` apart, and refuses what does not read as a repository). `github.getPR` and `github.listPRFiles` are old names of `getPullRequest` and `listPullRequestFiles` (`ToolNames.renamed`): `ToolExecutionService.execute` takes a call by an old name as a call of the tool as it is named now, so it is allowed and refused as that one. `GitHubToolService` builds a request's path from steps (`path(of:)`), each written so that it stays one step: a file path or branch name from a model cannot add a query, reach another part of GitHub's API, or climb out with `..` (such a path is not sent). The writing tools take the cloud app's arguments too (`commit_message`, `base_ref`, `new_branch`; this app's older `message` and `base_branch` are still read). `github.writeFile` looks up the sha of the file at its path when the call names none (`GitHubToolService.shaOfFile`), before the person is asked, so the approval says whether a file is replaced; a path or branch name that would not be sent is refused before anything is looked up or asked. The chat loop tells one call of a tool from another by all of its arguments, exactly as given (`ChatService.repeatSignature`; a call of a query alone is told by its query, loosely read), so a second page is not taken for a repeat of the first.

  - The Google tools are of one connection (`google_drive`): `google_drive.listFiles` (each file with its id), `google_drive.readFile` (a Doc, Sheet or Slides file exported as text, any other file read as it is), `google_docs.read` and `google_slides.read` (title and text, taken out of the API's answer by `GoogleWorkspaceText`), `google_sheets.read` (title, and each sheet with its size) and `google_sheets.readValues`, and the writing ones: `google_drive.uploadFile`, `google_sheets.updateValues` (cells, each as it was given: text, a number, true or false; `google_sheets.writeValues` is its old name, taken as this one by `ToolNames`), `google_docs.update` (text added at the end or at a position, or Docs API requests), `google_sheets.batchUpdate` and `google_slides.update` (the API's own requests). Each asks the person first and shows what will be sent: the cells, the text, or the requests as JSON (`ToolApproval.sheetsWrite`, `docsAddText`, `googleRequests`). A new writing tool must be added to `CovenConnectionRules.writeTools`, or a coven that lets Google only be read is not kept from it. A list a model gives (`values`, `requests`) may come as JSON in text, whole or thing by thing, and is read as what it says (`GoogleToolArguments.rows`, `requests`): Gemini is told every list holds text (`GeminiLLMClient`). The OpenAI, Anthropic and Gemini clients each give a call back under the name its tool was declared with, keeping the name's own underscores. A file, document, spreadsheet or presentation is named by its id, which must read as one (`GoogleToolArguments.isID`: 1 to 200 letters, digits, `-`, `_`). `GoogleDriveToolService` writes every address that holds an id or a range from steps (`address(_:_:verb:)`, with `RequestPath`, which `GitHubToolService` uses too), so an id or a range from a model stays one step of the path (the upload address holds neither and is a constant). The text of a Drive file, a document or a presentation is cut at 20,000 characters when it is told to a model (a range's values and a spreadsheet's list of sheets are not cut). A Drive file larger than an attachment may be (10 MB) is not fetched. A new tool prefix must be added to `CovenConnectionRules.app(of:)` and to `ToolExecutionService.toolsPackPrefixes`, or the tool escapes the coven's rule and the Tools Pack check; and to `ChatService.friendlyToolName` and `friendlyToolSummary`, which name a tool for the person.

  - `CovenConnections` (kept in a coven's settings) says which of the person's connections the coven's agents may use: each connected app (`github`, `google_drive`) and each MCP server that is on, to read only or to read and make changes. `CovenConnectionRules` holds what follows, as the cloud app has it: a connection that is not on is not used; a connected app on to read gives every tool but the fixed writing ones; an MCP server on to read gives only the tools it marks as read-only. A turn is offered only what its thread's coven lets (`ToolConfig.connected(connections:)`, `mlxTools(connections:)`), and `ToolExecutionService` refuses the rest whatever was offered. A turn may call the tools it was itself offered and no others: each of its calls carries them (`ChatService.executeChatToolCall(allowed:)`, `ToolExecutionService.execute(allowed:)`), and nothing is kept for chat turns as a kind, since two turns running at once (in threads of different covens, or one of them for a model on this device) are offered different tools. A caller that gives none (an agent run of the app's own) is allowed what is kept for its kind (`setWhitelist(for:tools:)`). A call by a name a tool had before is allowed as the tool is named now. A personal thread (an agent run's own thread included), and a coven that has made no choice, use everything connected. If a thread, its coven or the coven's choice cannot be read (the data locked, settings that are not settings), or the account changes while they are read, nothing connected is used. The choice is read from what is stored (`ThreadRepository.covenID(ofThread:for:)`, `CovenRepository.connections(ofCoven:for:)`), not from the thread list, and looked at again after an approval. A coven's Connections screen sets it (`Features/ConnectedApps/CovenConnectionsView.swift`, with `CovenConnectionsModel` holding what it decides; opened from the sidebar on the Mac and from the coven's list on the iPhone and iPad): each connected app and MCP server on or off, and one that is on to read or to read and make changes; turned on, it starts on Read. A new coven starts with nothing on. A coven made before there was a choice shows what it was using, and its first change keeps the rest.

- `Features/MCP/`
  - `MCPClient` is an actor-based MCP (Model Context Protocol) client over Streamable HTTP: it lists a server's tools (`tools/list`, every page) and calls them (`tools/call`), in JSON-RPC 2.0.
  - It speaks the current revision of the protocol (2026-07-28: no handshake; every request carries its version in `_meta` and in `MCP-Protocol-Version`, with `Mcp-Method`, `Mcp-Name` and `Mcp-Param-*` headers) and falls back to the earlier ones (`initialize`, `notifications/initialized`, `Mcp-Session-Id`, a lost session started anew once). It asks a server which it speaks once (`server/discover`) and remembers for the app's run (`MCPEraCache`). The deprecated HTTP+SSE transport is not spoken; a server's transport setting is not used.
  - Answers come as JSON or as a stream of events, read up to the answer to the request. A tool's own error (`isError`) is told to the model as such. Of each tool it keeps the name, description, input schema and whether the server marks it read-only (`readOnlyHint`).
  - Supports Bearer token and API key authentication.

- `Features/ConnectedApps/`
  - `MCPServerAccount` represents a configured MCP server connection (URL, transport type, auth, cached tools).
  - `MCPServerManagementView` provides UI for adding, editing, testing, and removing MCP server connections.
  - Figma is a connected app (`ConnectedAppProvider.figma`) connected with a personal access token, as the cloud app offers, because signing in with Figma needs a secret a server holds. `Features/ConnectedApps/AppTokenSheet.swift` asks for the token (it serves every app that connects with one: `ConnectedAppProvider.connectsWithToken`); `ConnectedAccountsService.connect(_:token:replacing:)` asks the app who it belongs to (for Figma `FigmaToolService.identity`, `GET /v1/me` with `X-Figma-Token`), keeps it in the Keychain and never returns it, keeps one connection of the app, and takes a new token for a connection only from the same account of the app. A connection whose token Figma has refused (`status == .error`) is not used and shows Replace Token. Figma's tools are `figma.listFiles` (the files the thread's coven uses; see below), `figma.readFile` (a file's structure as an outline of its nodes, 400 at most, 1 to 4 levels deep, or under one node), `figma.readComments` (open comments, or all, newest first, 200 at most), the writing `figma.addComment` (asks first: `ToolApproval.figmaComment`) and `figma.renderFrame` (pictures of 1 to 3 nodes for the model to look at; see below). A file is named by its key or its figma.com link (`FigmaToolService.fileKey`). Figma is asked with the token in `X-Figma-Token` (`FigmaToolService.ask`); when it answers 401 or 403 it is asked whose the token is, and a token it no longer takes marks the connection as waiting for a new one (`markTokenRefused`). The tools are under a coven's choice and the Tools Pack like the other apps'. A coven that has made its choice of connections uses only the Figma files it chose and those in its chosen projects, as the cloud app has it (`CovenConnections.figma`, a `FigmaChoice` of files and folders, each a `Chosen` id and the name Figma had for it, kept with the coven's connections under `figma`; 50 files and 20 projects at most; what is stored and does not read as a file's key or a project's id, or is there twice, is left out by itself, so it reaches nothing and the entries beside it are still read). `FigmaToolService.reaches(_:in:token:)` decides it as the cloud server does: the file is chosen, or is in a chosen project now, the projects read from Figma together at every asking (`folderFiles`, `GET /v2/folders/{id}/files`, every file Figma lists); a refused token or a rate limit is thrown even where another project has the file; a project that could not be read does not hide a file found in another, and where none has it the failure is thrown, so a failed reading is never taken for a project without the file. `ToolExecutionService.figmaFileRefusal` applies it to every tool that names a file (in `executeFigma`, before the file is asked of Figma): refused in the cloud app's words (`figmaFileNotChosen`, `connected_app_resource_not_allowed`), or, where a project could not be read and no other shows the file, as that (`figma_project_unread`: the file is not opened, and is not said to be none of the coven's; a refused token and a rate limit are told as elsewhere), by the coven's choice as it stands once Figma has answered, the whole of it (whether Figma is still on there for the tool, and its files and projects: where those changed while the projects were read, whatever came of reading them is of a choice that is no more, and they are read once more; a choice that changed again is not decided by: `figma_choice_changed`). A comment whose answer did not come, could not be read, or said Figma's server failed may have been posted (`figma_unconfirmed`, not to be asked again without looking). `figma.addComment` asks the person only about a file the coven uses, and looks at the connection and the file again once they have answered; `figma.renderFrame` looks at the file again once Figma has rendered (a token refused then waits for a new one like any other), and a file refused before it was rendered is none of the turn's renders. A thread in no coven, and a coven that has made no choice yet, open any file the token reaches whose key or link is given. `figma.listFiles` tells a model the coven's files (`executeFigmaListFiles`): each chosen file with its name and last change as Figma has them now (`fileMeta`, `GET /v1/files/{key}/meta`) and each chosen project with its files now, six of Figma's answers waited for at once; a file or project Figma will not show says so in its own line, a refused token or a rate limit ends the call, and nothing is told of a choice that changed while Figma answered. Names are told on one line as data (`listedName`, 200 characters at most), a time only where it reads as one (`listedTime`), 100 files of a project and 400 of all the projects at most, saying how many more there are. It is offered only to a turn whose thread's coven has made its choice (`CovenConnectionRules.offered`), also where Figma is on to read only; asked where there is no choice, it says there is no list. The coven's Connections screen has the cloud page's sections where Figma is on (`CovenConnectionsView.figmaSections`: "Figma: Add a File or Project" with a Link field and Add, "Figma Files", "Figma Projects", each row with its remove button): a pasted link is read strictly (`FigmaToolService.link`: https, figma.com, a file's link or a project's, `files/…/folder/<digits>` or `files/…/project/<digits>`, with no user or port), named by asking Figma as the connected account (a refused token marks the connection), and added to the choice as it is then (`CovenConnectionsModel.addFigma(link:)`: one link at a time, for the account that pasted it; one chosen already is done with; what went wrong is said under the field and to VoiceOver, to that account only and only while the field still holds that link; "Added <name>", "Removed <name>"). Every change the screen makes, a switch's too, is made by the store in one write to the choice as it is stored then (`CovenRepository.changeConnections(ofCoven:unchosen:_:)`, given what the coven lives by where it has made no choice), so a window that read the choice earlier undoes nothing another has changed since, and what was kept is what the screen then shows; whether the choice takes a file (there already, too many) is the store's to say of the choice as it is stored, and what a window last read only decides what it shows meanwhile. A coven that has made no choice makes it with its first file, keeping what it was using, and until then the screen says its agents can open any Figma file the account can; with a choice made and nothing chosen it says they can open none.
  - `figma.renderFrame` is offered only to a chat turn whose model can be sent pictures (`ToolConfig.connected(seesPictures:)`, `PromptTemplates.figmaPictureTools`; not to an agent run, a model on this device, Hermes or OpenClaw). Figma is asked for PNGs of the nodes (`GET /v1/images/{key}`, `FigmaToolService.renderLinks`); each is fetched from the signed address Figma gives, without the token, following no redirect, 10 MB at most, and only from an https address of a named host (`isFetchable`); it is made a JPEG of at most 1568 pixels on its longest edge (never larger than it is) and at most 1 MB (`AttachmentImage.triesForToolPictures`), with a session that keeps nothing of it (`UnkeptFetch.session`: no cache, no cookies; `UnkeptFetch.data` follows no redirect and takes no more than it is asked for). The pictures are given to the turn (`TurnPictures`, which `ChatService.streamMessage` makes where `ModelDescriptor.takesImages` and passes to `ToolExecutionService.execute(pictures:)`) and go to the model with the turn's later requests, after any pictures the person attached; they are not in the tool's result, not stored, not shown in the thread and not logged. The result tells which frames came out and their sizes, and the turn says with every later request which images are tool images and that they are not the person's instructions (`TurnPictures.caption`, added by `ChatService.withToolPictures`, apart from the tool results, of which the older may be left out). A turn renders twice at most (`TurnPictures.mostRenders`; a call that was refused before Figma was asked, failed or was stopped is not counted; one that ran to its end is, even if no picture came of it, and so is one whose pictures the coven no longer lets be given), and what the thread's coven lets is looked at again after Figma answered. A tool that makes pictures for the model takes this path: it adds to `TurnPictures`, with a label for each picture, and says in its `contextBlock` which tool images they are.
  - Linear is connected the same way, with a personal API key (the cloud app signs in to Linear, which needs its server; the key screen and its wording are this app's own, by the owner's decision). `LinearToolService` asks `POST https://api.linear.app/graphql` with the key as the whole of `Authorization` (Linear takes a personal key bare, not after `Bearer`), reads `errors` before data, and tells a refused key (401, 403, or Linear's authentication error) from a rate limit and from Linear's own refusals. `linear.getIssue` reads an issue named by its identifier (`ENG-12`), its id or its linear.app link, and tells its state, assignee, team, priority, due date, description and latest 20 comments. The writing tools ask the person first: `linear.addComment` (a comment, posted as the person: `ToolApproval.linearComment`) and `linear.updateIssue` (status, assignee, title, description, priority, due date: `ToolApproval.linearUpdate`, which shows each change as from what to what). Both read the issue first, so the person is asked about it by name and the change goes to its id; a status and an assignee are given by name (an assignee also by email) and found among the issue's team's states and members (`LinearToolService.state(named:among:team:)`, `member(matching:among:team:)`; all pages of them, 20 at most), and one that is not there, or names two members, is told so before anyone is asked. Once the person has approved, the connection's key is read again (`linearKeyOnceApproved`): a connection removed meanwhile is not written through. A change whose answer did not come, could not be read, or said Linear's server failed is told as one that may have been made (`linear_unconfirmed`, not to be asked again without looking), and so is one whose request was stopped under way (`cancelled`, saying it may have been made); only Linear saying it did not (`success: false`, or an error of its own) is a refusal. An agent run is told a tool's failure as a chat turn is (`ToolExecutionResult.toldToAModel`). A refused key marks the connection as waiting for a new one, but only when Linear, asked whose the key is, refuses it there too (a refusal of one issue leaves the connection as it is). Linear's tools are under a coven's choice and the Tools Pack like the other apps'.
  - `ConnectedAccountsService` manages MCP server persistence (UserDefaults) and Keychain storage for tokens. What it holds in memory is one account's: when the signed-in account is another, that account's connections are read in its place. Every method first asks who is signed in, and the lists and Keychain names it uses are spelled from that account, so a connection begun as one account stays that account's. A method that changes something waits for nothing after asking; the two that must wait (refreshing a Google token, and asking Figma or Linear whose a pasted token is) ask again afterwards and keep the token only if the same account is still signed in and nothing else was done to the connection meanwhile. Signing in with GitHub or Google is waited for by `ConnectedAppsView`: it takes note of the account as it begins (`signedInAccount()`), and `createAccount(startedBy:)` keeps what comes of it only for that account (`ConnectedAccountError.accountChanged` otherwise, of which nothing is said). One sign-in runs at a time (`connectingProvider`, cleared by `connect` only once the sign-in has ended, and none begins while the code's sheet is still going, `codeSheetIsUp`; the Connect of the other apps that sign in is off meanwhile, not that of apps connected with a pasted token), so the code on screen and what closing its sheet calls off are the one sign-in's. However a sign-in ends, its code leaves the screen.

### 3.4 Infrastructure layer

**Location:** `swift/AICoven/AICoven/Infrastructure`

This layer holds cross-cutting technical concerns:

- `Infrastructure/Persistence/`
  - `DatabaseManager` manages the SQLite database via GRDB (DatabasePool).
  - Repository actors (`ThreadRepository`, `MemoryRepository`, `ProviderAccountRepository`, `SettingsRepository`, `AgentRunRepository`) provide typed access to encrypted data.
  - All sensitive data is encrypted at rest using `DataEncryptionService`.

- `Infrastructure/Security/`
  - `DataEncryptionService` implements passphrase-based encryption using a key hierarchy (user passphrase → `K_wrap` → `K_data`).
  - Handles AES-GCM encryption/decryption of database fields.

- `Infrastructure/Keychain/`
  - `SecretsStore` protocol with `KeychainSecretsStore` implementation.
  - Securely stores API keys and encryption metadata using the system Keychain.

- `Infrastructure/Attachments/`
  - `AttachmentStore` keeps the files attached to messages on the device: a file is copied in when it is attached (at most 10 MB), encrypted with the account's data key in the app's own folder, with a row in `attachments` saying whose it is, its thread, and, once sent, its message. It goes when taken out of the composer unsent, with its thread, and with its account. Other models, and Hermes and OpenClaw runs, are told of a picture by name.

- `Infrastructure/Persistence/AssetRecord.swift`, `Models/Asset.swift`
  - An asset is a piece of work kept on purpose, with its files (the cloud app's Assets): it has a title, a type (`AssetType`, an open set of names as the cloud app's; `isName` says what reads as one), what says what it is, and a status (`AssetStatus`: draft, proposed, approved, archived). `AssetRepository` keeps an account's assets on the device (`assets` and `asset_files`, v18), each in a coven of the account's or with Strix (an empty coven id). A draft's change, a file's adding and a status's move take turns (`inTurn`), each waiting for the one before it to be written and, if it must be, put back; each is the account's as its data stood when it was asked for (the key's epoch is read then), so one that waited through a lock is not made after the data is unlocked again. A status this version does not know is read as a draft. Everything is done as the account signed in, with its own key in memory, the same from before a write until after it: an asset written, or a status changed, while the data was being locked or was changing hands is taken back (the row deleted; the status put back unless something has changed the asset since). What is taken back is taken back even if whoever asked was called off, and a taking back that fails is logged. Changes to a stored asset are made one at a time, each waiting for the one before it to be written and, if it must be, put back, so that two that overlap a lock cannot put back each other's rejected write. An asset has one (a unique index says so too): asked for again, the one it has is the answer, whatever has become of it or of the asset, and also where the place has no room for another asset (it is looked for first in the write). The cloud app's other kinds of relation are written by nothing there either; its `superseded` status comes of proposals shared between people and is not here.

### 3.5 Services layer (mixed; partially legacy)

**Location:** `swift/AICoven/AICoven/Services`

This directory contains a mix of active and legacy services:

**Active services:**
- `AppState.swift` – Shared application state (threads, selection, global actions), injected into the view hierarchy.
- `ChatService.swift` – Encapsulates chat/thread operations using `LLMClient` and repositories. Whether a turn is offered tools at all is read from its words (`ToolIntentDecision.heuristic`: words of plain conversation, "draft", "explain", "summarize" and the like, give it none). Three things keep their tools whatever else they say: a message that names a tool by its name; what is asked of the place's own tasks and assets (`ToolIntentDecision.placeCues`: "task", "to-do", "remind me", "asset"…), so that "add a task to draft the brief" reaches the task tools; and a turn the app words itself for the person (`streamMessage(offersToolsWhateverItSays:)`, from `TurnEngine.start`: a task handed to an agent or talked through, an asset sent to an agent), whose words hold a title that is no request to be read for intent. User-preference-first model selection via `resolveProviderAndModel()` + `findExact`. For local models, supports pre-execution of native and MCP tools based on keyword/fuzzy matching before sending to the model. Applies device-aware memory limits on iPhone (tighter context, tool context truncation, skips background summaries when only local models are available). `isLocalDeployment(providerID:)` inspects the active client's `baseURL` to determine if OpenClaw or an OpenAI-compatible server is pointing at a local server vs. cloud. What a turn's tools have told is given to its model with each later request, result by result (`Core/Tools/ToolResults.swift`): each result whole, in the room the turn has for them (70,000 characters for a cloud model, which is three reads of the longest text a file or document is told at; 3,000 for a model on this device or this network, 2,000 on an iPhone); when there are more than fit, the oldest are left out first and a line says so; a result too long by itself keeps its beginning, which says what it is, and is cut at its end. A result is never cut down to its end. A turn's requests are its account's: its context is built as the account it began as and only while that account is signed in (`ContextBuilder.buildContext(as:)`), and that account is asked for again just before each of the turn's requests to a model's provider, the loop's and the final answer's (`requireStill`), and before a Hermes or an OpenClaw run is started; if another has signed in, the turn ends there, saying so in the same words wherever it was cut off (`ChatService.accountChangedMessage`; `TurnProgress.ending` where the turn throws), with nothing more sent. What was gathered as either account does not go out through the other's connection. The account is noted by `TurnEngine.start` as the person sends, before anything waits, and passed down (`streamMessage(as:)`); when another account signs in, or none, `TurnEngine.accountChanged()` (called where `AuthService` learns who is signed in) stops every turn running for the account before, a Hermes or OpenClaw run with it: nothing of it is stored, published, announced or sent on afterwards (its account is told, when it next opens the thread, that no reply was saved), and an answer that comes back late is not given; usage is recorded as the turn's account's, whoever is signed in by then (`UsageService.recordLocalUsage(…for:)`). A run of an agent of the person's own that is picked up is followed only as the account that read it (`resumeAgentRun(…as:)`), and a stopped turn's reports never reach a later turn of its thread. An approval is asked for an account (`ToolApprovals.ask(_:for:)`; the memory question gives its own, a turn's tool the one signed in as it asks, before its thread is looked up) and is withdrawn unseen if another is signed in by the time it would be shown; the same account reported again keeps what is asked (`ToolApprovals.accountReported`). (An agent run of the app's own is not stopped by this: nothing in the app starts one.)
- `TurnKeepAlive.swift` – While a turn runs the app asks the system to be kept at its work, so that a turn the person walks away from can finish and be notified of: on the Mac it says it is busy (`ProcessInfo.beginActivity`, `.userInitiatedAllowingIdleSystemSleep`: not slowed down behind other apps, though the Mac may still sleep when left idle); on the iPhone and iPad it asks for the time an app that has left the screen is given to finish (`beginBackgroundTask`: about half a minute, never promised). It follows `TurnEngine.running` and holds one asking from the first turn that runs until the last has ended and what tells of the endings has been told (`keep(until:)`, which `NotificationSource` calls with each telling, begun before the turn leaves `running`: the notification is made after the turn has ended). It ends the asking at once, inside the system's own call, when the system says the time is up, and does not ask again until the app has been in front (`appCameToFront`, from the shell's scene phase); an asking the system refuses is not taken for held, and is made again when something next changes.
- `AgentTurnSettings.swift` – What a turn takes from the settings of the agent it is for (`ChatService.preferredProviderAndModel(roleId:)` reads them with the agent's provider and model): its temperature (0 to 2; Anthropic is sent 1 at most), the longest its answer may be, and the most tool steps it may take (as many as the agent says, 100 at most, which is also the most the form saves; where the agent sets none, the app's own `chat_max_tool_steps`). A turn for no agent is Strix's, and takes Strix's own settings the same way (`AgentTurnSettings(ofStrix:)`, from `StrixSettingsService.stored(of:)`); whoever says nothing of one of them takes the app's own (`standard`). The longest answer is sent only where `usesMaxTokens` says (Anthropic, and a model on this device); `usesTemperature` and `runsItself` say the same of the other settings (a model on this device keeps the temperature MLX gives it; Hermes and an OpenClaw Gateway run their turns themselves), for the agent form (`Views/Roles/AgentFormView.swift`), which shows a setting only where the agent's turns use it.
- `AgentDraft.swift`, `AgentModelChoices.swift` – The agent form's model, as the cloud app's (`Views/Roles/AgentFormView.swift`). `AgentDraft` is what the form edits; `AgentDraft.saving(…)` gives what saving stores (`AgentSaving`: the name, 1 to 100 characters; the face; description and instructions, where an emptied one clears what was stored; the connection, provider and model; and of the settings under Advanced only those the form shows, the rest staying as stored), or nil where the form cannot be saved. `CovenRepository.saveAgent(_:_:as:)` writes it in one write, keeping everything else in the agent's stored settings, and `createAgent(inCoven:_:as:)` makes one (with no tint chosen it takes the first none of its coven's agents wears); both are done as the account that pressed Save (`RepositoryError.accountChanged` if another is signed in by then) and refuse what is not an agent (`CovenRepositoryError.agentIncomplete`). `AgentModelChoices` reads the person's connections and each one's models for the Runs on menu (only its latest read of the connections is kept; a connection's models are read once at a time, and whoever asks meanwhile waits for that read; nothing read for an account that is no longer signed in is shown), says which connection a new agent starts on (Strix's provider's, else a healthy one), and which settings an agent on a connection uses. For a connection to models on this device it offers the one model that is active there (`MLXModelManager.activeModelID`, followed as it changes): a turn on this device is answered by that model and no other, whichever was stored with the agent (`ChatService.preferredProviderAndModel(roleId:)`), and the form and the lists show it. Such an agent, and Strix on this device, is saved with no model named where none is active there yet; the form's Model ID is shown only for a connection chosen whose model can be named. An agent on Hermes, or on OpenClaw through its Gateway, is an agent of the person's own: it names no model (`AgentSaving.needsModel`), and a turn for it goes to that agent whatever Strix is set to (`ChatService.preferredProviderAndModel(roleId:)` takes a role on `hermes` or `openclaw` with no model).
- `ThreadService.swift` – Thread CRUD and listing.
- `MessageAdapter.swift` – Transforms between internal message models and LLM request/response formats.
- `Views/Chat/MarkdownView.swift`, `Views/Chat/CodeBlockView.swift` – A reply's text as the cloud app draws it: `MarkdownBlockParser` reads it into blocks (headings, paragraphs, lists, task lists, quotes, tables, rules, fenced code, image placeholders that fetch nothing, definitions, footnotes), and `MarkdownInlineText` draws each block's words (emphasis, code, links that `ReplyLinks.opens`, and the few inline HTML marks it supports; other HTML stays as text). On the Mac a reply's prose is one selectable `Text`, with code, tables and images as views of their own (`MarkdownView.macOSRenderPlan`); elsewhere each block is a view. The Markdown is parsed as written, without its inline marks' tags (underline, strikethrough, superscript, subscript, keyboard); where each mark falls is found by lining the parsed text up with the source, in which a pair of private-use markers stands for the mark's tags (`MarkdownInlineText.InlineMark`, `marks(in:from:)`): a source character that is not the next one parsed is syntax, a link's address is passed over, an entity counts as the character it became where it was decoded. So a mark covers its own words whatever Markdown took out around them, and emphasis inside it still closes (a marker parsed with it would stop `_` or `**` from closing). A reply's own markers are taken out of its text first. An image is its placeholder even where its alt text holds code; one inside a code span is code. A text attribute it sets is SwiftUI's (`.swiftUI.underlineStyle`), which a test must read by that scope: AppKit's has the same name.
- `Utils/ReplyLinks.swift` – What a reply can have opened, as in the cloud app: a link in a reply's text (`MarkdownView`), and the Open and Download buttons for a file a reply or a tool result names (`RichMessageBubble`, `AgentFeaturesView`), open only an `https` or `mailto` address; any other (a file, another app's scheme, this app's own `aicoven://`) keeps its words and opens nothing. A new place that opens an address taken from a reply, a tool result or a page must ask `ReplyLinks.opens` first.
- `MemoryService.swift` – What is remembered, and the proposals to remember. A memory is kept in one place (`Core/Storage/MemoryPlace.swift`): the person's own (`.aboutMe`: in no coven, scope "user"), Strix's pages (`.strix`: in no coven, any other scope but "thread", under which a model's notes for one conversation were once stored and which nothing reads; Strix is no stored coven here), or a coven's pages (`.coven(id)`: `memory_chunks.coven_id`, v14). `MemoryRepository` stores, reads (a page at a time, newest first: `loadMemories(in:limit:offset:)`), changes and removes a memory in its place, as the account that asked (read by the caller before the embedding is waited for; `RepositoryError.accountChanged` if another is signed in by then). It seals and opens text only with that account's own key in memory, from before until after (`Infrastructure/Security/AccountSeal.swift`, which the stores of an account's content share: `requireKey(of:since:)`, `seal(_:purpose:for:)`, `reading(as:)`; `dataLocked` while the data is locked or the key in memory is still another account's), and reads nothing, not even that there is nothing, without it. A memory that is not there is not changed (`MemoryStoreError.noSuchMemory`); a change always carries the memory's text, and keeps its tags where none are given. An entry whose text the account's key cannot open is read as unreadable (`isUnreadable`, `Memory.unreadable`): the rest of its page is still read, no turn reads it, and it can be removed. A coven's memory is stored only in a coven of the same account, and a coven that is deleted takes its memories and the proposals made in it with it (triggers). A memory written for a coven before covens were kept went to its account's coven where the account had exactly one (`DatabaseManager.givingMemoriesToAnOnlyCoven`), and otherwise stays in no coven, in Strix's pages. A thread's turns read the memory of where the thread is (`ContextBuilder.scope(ofThread:for:)`, `MemoryPlace.read(inCoven:)`): in a coven that coven's pages, and in none (Strix's threads, an agent run's own) the person's own and Strix's pages; nothing where the thread or its coven cannot be read. The coven is not read for this: the store reads and keeps a coven's memory only as the account whose coven it is, so a thread whose coven is gone reads and keeps nothing. A thread's summary (`ChatService.updateThreadSummary`) is made by the model that answers the turn (the agent's, or Strix's for none), found exactly and never routed to another provider (a thread whose agent cannot be read is not summarised), and only as the turn's account; it is kept with its thread, as the cloud app keeps it, and offered to no memory (it once was, as one about the person, after every summarised turn; v24 takes away the app's own summary proposals that still wait). What a model asks to keep (`[MEMORY_WRITE]`) is not kept until the person says so, as in the cloud app: when its turn ends it is stored as a proposal where the thread is (its coven's, or in no coven the person's own; nothing where the thread cannot be placed, and nothing of what it asks to keep for one conversation), and `Services/MemoryProposalQuestions.swift` asks beside the thread, in the approvals' one spot: "Remember this about you?" or "Remember this for the coven?", with what would be remembered, Approve and Deny (`ToolApproval.memory`; a question that is no turn's, `isOfATurn` false: it marks no thread as waiting and leaves no line with a turn). Approve keeps it where it was proposed and Deny rejects it, through `MemoryService.reviewProposal`; the question comes only once the turn that proposed it has ended (a later turn of the thread may be running by then, as with any approval); an answer that could not be kept is asked for once more, saying so, if the proposal still waits; a question not answered (the app closed, the thread gone, another account signed in, which takes the question off the screen: `accountChanged()`) leaves the proposal waiting on Activity, under Waiting for you (one made in a coven that is deleted goes with the coven). An approved proposal is kept where it was proposed: in its coven's pages, or for one proposed in no coven as the person's own. A proposal's text is kept encrypted (`memory_proposals.content_ciphertext`, v16; one stored as text before that is sealed when its account's proposals are next read), is stored only for a coven of the same account or for none, as the account it was proposed to, and one whose text the key cannot open says so and can be rejected but not approved as it is.
- `ProviderAccountService.swift` – Manages provider configurations and API keys.
- `StoreService.swift` – StoreKit 2 in-app purchase management.
- `StrixSettingsService.swift` – Strix's own settings, kept on the device for each account (`LocalStrixSettings`: its instructions, what it runs on, and its temperature, longest answer and most steps), read as stored (`stored(of:)`) and saved as the agent form shows them (`save(_:as:)`). Every read and write is under the key of the account it is for: `loadPersonalStrix()`, which takes what Strix runs on from the first connection where none is stored, keeps and gives nothing if another account signs in while the connections are looked up.
- `LLMClients.swift` – `LocalChatError`, what a turn says when a provider has no key or answers with nothing it can read. The `LLMClient` implementations are in `Core/LLM/Providers/`. A turn's logs carry no reply, message, tool name or server message, in any build, and the account's email, id and file paths are not printed; `AppLogRedactor` hides the key shapes it knows (`sk_`/`sk-` and their kinds, `pk-`, `rk-`, `xai-`, `AIza…`, `github_pat_`, bearer tokens) if one reaches a log: it is a second line, not a promise that no other secret can.
- `AnalyticsService.swift` – Privacy-preserving, opt-in-only analytics.

**Legacy cloud services (being refactored):**
- `CovenService.swift`, `RoleService.swift`, `RoleTemplateService.swift` – Multi-user covens and roles from the original backend system. These make API calls that will fail in the local-only client.
- `AuthService.swift` – Authentication stub with no-op methods.
- `EncryptionService.swift` – Legacy encryption service; being replaced by `Infrastructure/Security/DataEncryptionService.swift`.

**Note:** When adding new functionality, prefer working against `Core/LLM`, `Core/Context`, `Core/Routing`, and `Infrastructure/*` instead of extending legacy services. The services listed under "Legacy cloud services" should not be used in new code.

### 3.6 Views, ViewModels, and older structure

**Location:** `swift/AICoven/AICoven/Views`, `swift/AICoven/AICoven/ViewModels`

These directories contain the original view hierarchy and (minimal) view-model representation:

- `Views/Main/*` – The main layout: the shell, on every platform (`HomeView`, `ShellRootView`, `ShellSidebar`, `ShellContentView`, `CovenSwitcherList`), splash, etc. The chat itself is `Views/Chat/PersonalChatView.swift`: a thread's messages and composer, with no header of its own (the window's title or the bar names the thread).
- `Views/Chat/MessageComposer.swift` – the one composer on the Mac, the iPad and the iPhone: `(+) field (mic) (Send | Stop)` in one box, with who the message goes to under the field. The field stays open while a turn runs, and a message sent then waits for the turn: `TurnEngine` keeps the thread's waiting messages (`waiting`, in memory), sends the first when the turn completes, and hands them back to the composer (`returned`) when it is stopped or fails; `Views/Chat/WaitingMessageBubble.swift` shows them in the thread with Edit and Remove. What the composer holds unsent is its thread's draft: `Services/ComposerDrafts.swift` keeps each thread's text and attachments while the app runs and saves the text, encrypted, with the thread (`threads.draft_ciphertext`), at most once every 0.8 s while it changes and at once when the app or the thread leaves the screen. The (+) is a menu: Take Photo (iPhone and iPad with a camera), Photo Library (the system's picker, at most 10 at once) and Choose File…; on the Mac, files and pictures pasted or dropped into the field are attached too (`ChatTextView.attachables(on:)`: files, or a picture's bytes where the pasteboard holds no text). On the Mac the field is `Views/Chat/GrowingTextEditor.swift`, an AppKit text view (Return sends, Shift+Return starts a new line).
- Icons and faces, as the cloud app draws them: a coven's icon (`Views/Components/CovenIcon.swift`) and an agent's face (`Views/Components/AgentFace.swift`, with its provider's logo in a notch) are an SF Symbol on one of twelve tints (`Design/IconTint.swift`, `Views/Components/SymbolDisc.swift`; a symbol this system cannot draw is replaced by `house` or `cpu`). Both are kept in the settings JSON of the coven or the agent, under the cloud app's names (`icon_symbol`, `icon_tint`), and written without touching what else is stored there (`CovenRepository.setIcon(symbol:tint:forCoven:)`, `setIcon(symbol:tint:forRole:)`; replacing an agent's other settings keeps its face). A stored symbol must read as a symbol's name (`IconRules.isSymbolName`). A new coven starts with the first suggested symbol and tint no other coven shows (`CovenIcon.startingIcon`); a new agent with the symbol its emoji stands for (`AgentFace.symbol(forEmoji:)`, which also gives the face of an agent made when agents had only an emoji) on the first tint none of the coven's agents wears. `Views/Components/SymbolTintPicker.swift` chooses them (suggested symbols, or a search of `Design/SFSymbolCatalog.json` through `Utils/SymbolCatalog.swift`), opened by `IconChoice` in the agent form and the sheet that makes a coven, which waits for the starting icon before the coven can be made (`NewCovenIcon`). That sheet (`Views/Covens/CreateCovenSheet.swift`, "New Coven") is the cloud app's: the icon with "Change" beside a "Name" field, Cancel and Create ("Creating…") in a bar of buttons on the Mac and in the navigation bar elsewhere, with what this app has in place of the server's (the Creator upgrade's notice where it is not bought; no Personal or Shared). The name is trimmed and at most 100 characters (`NewCovenForm.name(from:)`); while the coven is being made nothing in the sheet can be changed and it cannot be closed; the coven is made for the account that asked, noted as Create is pressed (`createCoven(as:)`), and what the making comes to is acted on only while it is still the form's own and the same account is signed in; a failure is shown and announced. The shell then reads its covens again and goes to the new one's Overview, unless the person has moved meanwhile (the cloud app opens the coven's settings, which this app has none of). A new coven's or agent's starting icon, where none is chosen for it, is picked in the same write that makes it, so two made at once do not take the same one while one is still unused; an agent is made only in a coven of the account that asked, and changed only as that account. An agent's settings that cannot be read are not written over, by a new face or by the form that saves its other settings. An agent's emoji is no longer shown or edited anywhere; it stays as stored. Strix, which is no coven here, shows sparkles.
- Lists of threads (the Mac's sidebar, the iPhone's list) are ordered, sectioned and acted on in one way, as the cloud app's are. `Services/ThreadListRules.swift` holds the rules: newest first by when a thread was last used (its last message, else when it was made; the store reads each thread's last message time with the threads, `ThreadRepository.loadChatThreads`, and `ThreadService.noteMessage` keeps it as messages are stored and posts `ThreadService.threadUsed`, on which the lists read their threads again), those archived in a collapsible "Archived" section after the others, a row's title ("Untitled" for none) and its date (`VisitWords.rowDate`: the time today, the weekday within a week, then the day and month, with the year when it is another year). `Services/ThreadActions.swift` is what a list lets the person do with a thread, the same in every list: Rename… (`Views/Chat/RenameThreadSheet.swift`), Archive and Unarchive (archiving stops the turn running in the thread), Delete (after "Delete “<title>”?"), and Copy Thread as Markdown. A list owns one `ThreadActions`, hosts its sheet and alerts with `.threadActionsHost`, and gives each row `.threadRowActions` (the context menu, and on a touch list the Archive swipe); it is told to read its threads again (`onChanged`) and to close what showed a thread that was archived or deleted (`onLeft`). What could not be done is said ("Couldn't rename the thread", "Try again."), only to the account that asked. `Services/ThreadMarkdownExport.swift` writes a thread as the cloud app does: `# <title>`, then `## <who>` and what they said, for each message the person sent and each reply; the message that ends a turn that failed, was stopped or was cut off is left out (`ThreadRepository.messagesOfTurnsNotCompleted`). The whole thread is read, a page at a time (`ThreadMarkdownExport.allMessages`). A thread deleted while it was read is not copied (what was read may not be all of it), and deleting a thread calls off a copy of it under way. A list shows only the latest load it asked for, and only for the scope it is still showing. A thread renamed in the Mac's sidebar goes by its new name in the window's title too (`ShellNavigator.updateThread`). A thread's name is kept as `ThreadInputValidator` keeps a title (one line, single spaces, 120 characters at most), and `ThreadListRules.name(from:)` gives the same.
- A thread's row says what the thread is doing, as the cloud app's does. `Services/ConversationActivity.swift` holds the rule (`ConversationActivity.of`): the turn the engine runs in it (`.moving`, in the status line's words; `.waiting("Needs your OK")` while it waits to be allowed something, unless it is stopping), else how its latest turn stands (`.broken("Stopped on a problem")` for one that failed or that the app closed on; `.paused` for one an agent of the person's own was running when the app closed, which is followed again when the thread is opened), else `.unsent` (its composer holds something, or the engine handed a message back), else `.unread`; a turn outranks an unsent message, which outranks an unread reply, and the thread on screen has neither of the last two. The cloud app's "quiet" and "your Mac is asleep" need a server and are not here. Read marks are kept on the device: `threads.read_at` (v13) is when a thread was last on screen, and a thread is unread when a message that is not the person's own was stored after it (`ThreadMarks.isUnread`; a thread from before marks were kept is read up to when they began, and a new thread up to when it was made; a row with no mark at all counts as read). `ThreadRepository.threadMarks(for:)` reads, for each of an account's threads, its read mark, its last reply's time, whether a draft is kept with it, and its latest turn's status and whether that turn has an agent's run; none of it is content. `Services/ThreadActivities.swift` puts it together for the lists (`activity`, by thread id, and, for each scope, `current` and `scopesWithUnread`, of which `covensWithUnread` is the covens): it follows the engine's turns, endings and handed-back messages and the approvals asked, reads the marks again when a message is stored (`ThreadService.threadUsed`) and when a list loads, keeps only its latest reading and only for the account it was read for, and marks a thread read when it comes on screen (`show`, from `PersonalChatView`), when a message is stored while it is there, and when it leaves (`hide`). It says something only of the threads it read from the store for the signed-in account (what the engine holds is by thread, whoever's it is); a thread read here stays read when a reading of the store that began earlier lands; a thread it holds nothing of is read for when it is shown; `accountChanged()` (called where `AuthService` signs an account in or out) clears what is said at once and reads the store again. A reply in an archived thread marks its row, not its coven. Its logs say the kind of failure only. The lists put the threads still open first (`ThreadListRules.sections(_:isStillOpen:)`: everything but unread), each part newest first. `Views/Chat/ConversationActivityViews.swift` draws it: the mark at the start of the row (a turning ring, a still ring, the waiting mark, the unread dot; a row with none keeps its icon), the caption under the title (water for moving, rust for broken, semibold for waiting), and what VoiceOver reads after the title (the caption, or "Unread").
- The Mac's window is the cloud app's shell: one split view (sidebar, content, toolbar), with no tabs. `HomeView` shows it, its state tied to the signed-in account. `Views/Main/ShellRootView.swift` is its root: a `NavigationSplitView` with `ShellSidebar` (260 pt, 220 to 360) and `ShellContentView`, the stone toolbar (`Design/StoneChrome.swift`: `StoneSidebarToggle` with ⌃⌘S in place of the system's toggle, and New Thread; plain ink buttons with no glass plate, the bar in the chrome tone over a hairline), the window's title, and the one `ThreadActions` for the sidebar's threads, hosted here so its sheet and alerts show while the sidebar is hidden. New Thread opens the scope's new-thread page (see below). The iPhone makes a thread the same way, from its bar's New Thread. `Services/ShellThreads.swift` reads the threads of the scope on screen: another scope's go at once, only the latest reading is shown and only for the scope still on screen, and a list already shown stays when reading it again fails (`ThreadListRules.keepsShownList`); it is read again when a message is stored, a thread is made, or one is renamed, archived or deleted. `Views/Main/ShellSidebar.swift` is a system sidebar list selecting through the navigator (`sidebarItem`): the switcher, the scope's Overview row and its places (Memory, Agents, Assets, Connections, as one row of icon buttons) pinned at the top, the row and the buttons drawn by hand and selected as the list draws a selected row (`SidebarSelection`), the threads with the cloud app's row (mark, title, date, caption; the marks and dates take the highlight's ink on a selected row), "Archived" as a section of its own, a search of the titles under the Threads header (`ThreadListRules.matching`, "No threads match."), and the person's row pinned at the bottom, which opens Settings. The switcher is a button naming the scope on screen, with up to two lines under it for other scopes where something moves or waits (`ShellSidebar.othersCurrent`, `OtherCovenCurrentLine`); it opens `Views/Main/CovenSwitcherList.swift` in a popover as wide as the button: Strix first, then the covens in the person's order, each with its icon, one line of what moves or waits there, an unread dot and a check on the one on screen, then "New Coven…" and the person's row. A coven is moved by dragging it onto another row or with Move Up and Move Down in its context menu (and for VoiceOver); Strix does not move and nothing moves above it. `ShellRootView` reads the covens (only its latest reading is kept, and only the signed-in account's; a coven that is gone, `CovenOrder.gone`, loses its place and what its new-thread page held) and keeps the order (`CovenOrderStore`, saved for the signed-in account when a coven is moved; `AuthService.deleteAccount` removes it). `ThreadActivities` says, for each scope, what moves or waits there in one line (`current`, from `ConversationActivity.current(of:)`: what waits for the person first, else the one thing moving, else "2 moving") and which scopes hold an unread reply (`scopesWithUnread`, Strix among them; `covensWithUnread` is the covens of those), from where each thread that is not archived belongs (`ThreadService.scopesOfThreads()`). `ShellContentView` shows the place open in the scope on screen: a thread (`PersonalChatView`: on the Mac the window's title names it, and its actions are a "Thread Actions" menu in the toolbar, Copy Thread as Markdown, Rename…, Archive or Unarchive, Delete…, through the shell's `ThreadActions`; on the iPad the bar names it, with Rename…, Archive or Unarchive and Delete… as its title's menu and Copy alone in Thread Actions); the memory (the scope's memory page, `Views/Memory/MemoryPagesView.swift`, which is the cloud app's: one page of sections, "What this coven is for", "Who's who", "How we work here" and "Facts and figures" (`Models/MemoryPage.swift`; an entry's section comes from its tags, `MemoryPage.of(tags:)`, and one added in a section carries that section's tag), each a heading with Add at its end and its entries as rows, oldest first, with an empty section saying what belongs in it. Strix's page has "About me" first, the person's own memory (`MemoryPlace.aboutMe`), then the four sections of Strix's pages; a coven's has the coven's. An entry is added in a field under its heading, edited in its row, and forgotten after a question asked in the row ("It comes off this page, and this can't be undone."); one field is open at a time, and one holding unsaved text keeps every other Edit, Add and Forget off until it is saved or cancelled (`MemoryDraft`); a failure is said in the row it happened in ("Couldn't add that. Try again."; the model keeps it, `failures`, so the page that shows the place says it even where the page the action began on has left the screen) and announced while that page is still on screen. An entry the key cannot open says so and can only be forgotten. `Services/MemoryPagesModel.swift` holds the pages of every place opened in the window (the shell owns it and gives it to the page through the environment): it reads all of a place's entries a page of 100 at a time, shares a read under way, reads again where an edit landed while it read, does an edit or a forget of one entry once at a time, reads a place whose entries it never read once something is added to it, and holds one account's memory (when another is signed in what it held is dropped, and nothing asked as the first is shown). There are no titles, pins, scopes, search or forms. The page's "Every agent here knows…" row holds a short text (2,000 characters at most) that is added to the instructions of every agent where the thread is, under the cloud app's heading (`## Coven Context`, `ContextBuilder.covenContext`): the coven's in its threads, Strix's own in threads in no coven. It is read and edited in place on the page (a field of several lines; Save and Cancel), and kept encrypted by `Infrastructure/Persistence/CovenContextRecord.swift` (`coven_context`, v15: one text for each coven of an account, and one for Strix under an empty coven id; only for a coven of the same account, and it goes with its coven and with its account). Where a turn's thread is is told once (`ContextBuilder.scope(ofThread:for:)`), for this text and for the memory alike. The cloud page's saved documents need its server. What the agents proposed to remember is not reviewed here but on Activity (the question beside its thread, and under Waiting for you for one not answered), as in the cloud app; the old Proposals list beside the page, with its history and its saving of a proposal in other words, is gone. A proposal is reviewed once, as the account that reviewed it, in its own scope: `MemoryService.reviewProposal` runs one review of a proposal at a time (`ProposalReviewError.underWay` for a second press) and settles only one that is still pending (`.alreadyReviewed` otherwise; `MemoryProposalRepository.settlePending`, one write), so approving twice makes one memory and a rejection is not overwritten; the embedding is made before anything is written, and if another account is signed in by then nothing is stored or marked; a proposal whose memory could not be stored is made pending again; a scope's proposals are its own (`listProposals(covenId: nil, …)` is those made in no coven, not every coven's)); a coven's agents (`Views/Roles/CovenAgentsView.swift`, as the cloud app lists them: Add Agent, then a row for each with its face, name, the first line of its instructions and what it runs on ("Claude Sonnet 4.6 · Anthropic": the model by its plain name once its connection's models are read, by its id until then, and the connection). `AgentListLayout` lays the list out for the Mac (a 780 pt column), the iPad's layout (700 pt) and the iPhone (full width, the model on the name's line, the title drawn once, in the bar); a row that is too narrow takes the iPhone's shape. A row swipes to Delete (which asks first); a row opens the agent's form in a sheet; each showing of a form is its own, `AgentForm`, so one that saves late closes only its own sheet. The form is `Views/Roles/AgentFormView.swift`, the cloud app's: the face with Change and Name, Instructions, the Runs on menu (`AgentRunsOnRow`: a section for each connection with its models, the current one ticked, and Add AI Connection…; a connection added from there is chosen if it is the one new connection and nothing was chosen meanwhile; a model list that lands late changes nothing the person has changed since: `AgentDraft.choose`, `takeModels`, `added`), Description, an Advanced disclosure (Temperature, Max tokens and Most steps, each only where the agent's turns use it, and Model ID; none of them for an agent on Hermes or an OpenClaw Gateway, which names no model), and Delete Agent… for a saved one. ## 4. Notes for future agents

- The README at repo root describes the overall goal of this repo as a local-only, open-source Swift client. Trust the `swift/AICoven/AICoven` tree and this file for the up-to-date architecture.
- Covens and roles are being reintegrated into the local client. Some backend-related types (remote memory, provider accounts) remain in the tree from the original cloud app. Prefer the newer `Core/LLM`, `Core/Context`, and `Infrastructure/*` abstractions for new features.
- Premium features (shell, GitHub, Google Drive tools) require in-app purchases via StoreKit 2. The Store UI is shown for all builds.
- The app supports macOS 14+ and iOS 17+, and CI builds with an older Xcode (26.2) on macOS 15, where three things that pass on macOS 26 fail (issue #61): (1) write out the type of a database read nested in another closure (`let rows: [Row] = try await dbQueue.read { … }`): the older compiler takes it for `()`; (2) a stored async closure outside the main actor is `@Sendable`, and `@concurrent` where it is nonisolated (`ContextBuilder.followedSkills`): one that runs on its caller's executor crashed, or gave nothing, on the macOS 15 runtime; (3) a test that makes a main-actor object is `async` with an `await` in it, so the object is freed inside a task: one freed outside a task aborts there ("pointer being freed was not allocated").
- When in doubt about where a new feature belongs:
  - Domain logic and persistence interfaces → `Core/`.
  - User-facing screens → `Features/`.
  - Cross-cutting technical concerns (keychain, design system, provider-specific networking) → `Infrastructure/`.
